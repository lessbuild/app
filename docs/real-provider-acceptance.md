# Real-provider release acceptance

Run this on a disposable staging project in a dedicated DigitalOcean, Hetzner, or Vultr test account. It creates real infrastructure and can incur provider charges, so the operator must perform the actions deliberately through BuildPusher. Record the UTC start time before creating anything; the audit's `--since` filter prevents an old or partially unrelated run from passing the release gate.

1. Connect a restricted cloud token and a source-control provider.
2. Create a fresh server and wait for every provisioning stage to finish.
3. Create a website and application environment, enable health monitoring, and deploy a known test repository.
4. Verify the deployed immutable revision.
5. Deploy a distinct second revision, then roll back specifically to the first revision.
6. After the rollback, configure and verify a disposable HTTPS offsite backup destination, create a backup, mutate disposable data, and restore that exact backup.
7. Confirm the restored data, then run and retain a successful health check after the restore completes.
8. Run `php artisan buildpusher:acceptance:audit PROJECT_ID --provider=PROVIDER --since=START_TIME --json` and retain the output as release evidence. Both filters are mandatory: `PROVIDER` must be `digitalocean`, `hetzner`, or `vultr`, and `START_TIME` must be the ISO-8601 UTC time recorded before step 1. The command rejects a missing filter so stale or cross-provider evidence cannot accidentally satisfy the release gate.
9. Delete the disposable server and confirm it disappears from the selected provider.

A passing command verifies recorded lifecycle evidence, not complete release acceptance. JSON explicitly identifies this scope and lists outstanding external verification. Retain a comparison of the restored application fixture with its pre-backup contents, provider-side cleanup confirmation, and evidence that the drill used real infrastructure. Seeded or manually inserted database records cannot establish those facts. Capture the audit before cleanup because deleting resources can remove their associated history.

Successful backup jobs now record HTTPS transport evidence on the backup itself. Later destination verification does not change that historical evidence. Existing backups are not backfilled: run a new backup after applying migration `2026_09_06_000000_add_backup_transport_evidence` for acceptance eligibility. A successful HTTPS transfer alone does not prove independent hosting or data integrity; those remain operator checks.

The audit fails until one project environment has recorded an ordered lifecycle after the start time. It requires a provider-assigned server identifier, two distinct immutable source revisions, a rollback linked to the first revision and its artifact, a later backup with its own HTTPS transport evidence, a restore of that exact snapshot, and a successful health result after the restore. It examines alternative rollback and backup candidates, so an incomplete later attempt does not hide a complete earlier chain within the requested window. Resource ownership and placement must agree. It does not expose credentials, logs, addresses, or backup identifiers.

## Configuration-as-code acceptance drill

Use this extension for the current configuration feature before advancing to preview environments. The generic audit above does not inspect configuration reviews, application receipts, deduplicated intents or environment removal. Passing it alone is insufficient.

### Required target and evidence

Before execution, record the authorized disposable provider/account or server, region, resource-size limits, maximum spend, cleanup owner and UTC start time. Identify a controlled fixture repository with two immutable revisions and disposable data, a disposable HTTPS offsite backup destination, and the workspace/project owning every binding. Never infer spending authorization from an existing credential. An existing server can establish deployment behavior, but does not satisfy the fresh-provider-provisioning part of the generic release drill.

Keep a private evidence directory outside the repository. Save sanitized plan/review/receipt responses, revision IDs, fixture checksums, audit JSON, timestamps and provider resource inventory. Do not save bearer tokens, plaintext secrets, raw encrypted snapshots or credential-bearing command output in the published record. Record each check as passed, failed or not run; missing evidence is not a pass.

### Execute through the supported workflow

All API paths below are relative to `/api/v1/projects/{project}` and require the existing manager/token entitlement and network-policy checks. The browser's Configuration as code workflow uses the same reviewed operations. Obtain IDs from the selected disposable workspace, not example IDs.

1. **Baseline and plan.** Record the project's environments, child configuration, build IDs and operation IDs. Use a version 2 document with a staging environment, explicit placement, supported runtime, one named process/resource, a disposable secret reference and `deploy: {repository: app}`. Supply the matching `placements`, `secrets` and `repositories` bindings described in [the contract](application-configuration.md). POST `/configuration/plan`. Verify the response names the intended objects and reveals no secret values. Re-read the baseline and confirm planning created no objects, builds or operations.
2. **Review and exact apply.** POST `/configuration/reviews` with that document and bindings. Save its ID, plan and expiry. POST `/configuration/reviews/{review}/apply` with an empty body. Save the application receipt. Verify local topology and encrypted-variable behavior through the supported UI/API. A local receipt is not remote deployment success.
3. **Delivery.** Observe the receipt at `/configuration/applications/{application}` and the actual build until terminal success. Confirm the deployed immutable revision and fixture response on the disposable target. Preserve the mapping from review to application to operation to build to revision. Confirm the scheduled processor and queue worker handled the real operation; an empty processor run is not this evidence.
4. **Idempotency.** Apply the same review again, then create/apply an unchanged review. Verify the receipt reuse/shared operation rules: no new remote resource, secret version or deployment attempt. Preserve before/after IDs and counts rather than relying on a success message.
5. **Freshness and ownership.** Create a review, then change a disposable reviewed input through its supported editor. Verify applying the old review is rejected and creates no new deployment. Restore the input and create a fresh review. Attempt a binding from a separate disposable workspace and verify rejection without exposing the foreign resource. Do not use a real customer's workspace for this test.
6. **Cancellation and retry.** On the disposable project, arrange an existing deployment approval/window gate before applying a changed deployment intent. Cancel the resulting pending operation through `/configuration/applications/{application}/operations/{operation}/cancel`; repeat the request and confirm no build starts. Restore the gate, then explicitly retry via the corresponding `/retry` endpoint. Repeat the retry request and confirm one replacement identity and at most one deployment. Observe actual completion and retain both original and replacement history. Do not pause the host's shared worker merely to manufacture this case.
7. **Failure recovery.** Use a controlled, reversible failure in the disposable fixture or target, with its recovery action documented before starting. Confirm a real failed build remains visible and polling/reapplying does not silently create another attempt. Remove the transient failure without changing the reviewed deployment inputs, then explicitly retry and verify a single successful replacement. If recovery requires changing inputs, verify the old retry is rejected and use a fresh review instead; record that separately from same-snapshot retry success.
8. **Release lifecycle.** Perform the second-revision deployment, rollback, offsite backup, disposable-data mutation, exact-backup restore and post-restore health verification from the generic drill above. Verify restored fixture contents against the pre-backup checksum. Retain the audit output before deleting anything. Do not claim provider provenance or restored-data equality from database history alone.
9. **Whole-environment removal.** Ensure all configuration operations/builds are terminal and remove disposable scheduling/preview/load-balancer dependencies through their own workflows. Submit `version: 2` with `remove: {environments: [staging]}` and empty bindings. Verify the plan enumerates every owned child and explicitly preserves remote services/data. Apply it; verify the environment and owned local children are gone while the website, repository, builds and receipts remain. Reapply the same review and review removal again to verify receipt reuse and the absent no-op. Independently verify the remote workload/data still exist; local removal is not remote cleanup.
10. **Provider cleanup.** Inventory all resources created by the drill, including servers, volumes, managed services, addresses, DNS records and offsite backup objects where applicable. Delete only the approved disposable resources through their own supported cleanup workflows. Confirm absence independently at the provider and retain the final inventory. Document any retained resource, reason, owner and continuing cost; do not mark cleanup passed while an unintended resource remains.

### Completion record

Record the selected target and authorization, UTC interval, source revisions, sanitized identity chain, per-step result, restored-data comparison and independent cleanup evidence. Link the generic audit JSON and explain its narrower lifecycle scope. Configuration acceptance requires the configuration-specific checks above as well as the relevant real deployment/recovery evidence. The production schema rollout at [the September 8 checkpoint](verification/configuration-rollout-2026-09-08.md) proves data-preserving installation and readiness, not completion of this drill.

## DigitalOcean scoped credentials

BuildPusher tests DigitalOcean connections with `GET /v2/droplets?per_page=1`, requiring `droplet:read`. A deployment-scoped token can legitimately lack `account:read`; a 403 from `/v2/account` alone does not invalidate droplet access. The successful connection check does not prove permission to create/delete droplets or SSH keys. Verify the needed creation and cleanup permissions before provisioning. See [DigitalOcean's scope reference](https://docs.digitalocean.com/reference/api/scopes/) and [droplet creation dependencies](https://docs.digitalocean.com/reference/api/scopes/droplet/create/).
