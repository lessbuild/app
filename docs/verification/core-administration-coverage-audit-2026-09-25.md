# Core administration coverage audit — 25 September 2026

## Finding

Core has implemented shared workspace administration and several product-backed management surfaces, but the administration catalog still contains substantial product-host handoffs. The catalog is an authorized directory and search index: `WorkspaceAdministrationCatalog::forMembership()` creates Core URLs only for `core.*`/`platform.*` routes and sends every other route through the product-origin resolver. A visible/searchable catalog entry therefore proves discoverability, not that the page or its mutations have moved to Core.

The remaining-source checklist correctly calls for replacing remaining handoffs with real Core pages/actions, but its named gaps are partly closed in source. Deployer now has bounded project preview and environment settings; Monitor has alert/destination/maintenance/SLO desired-state/settings and existing mapped application/environment/check edits; Analytics has site/goal/data providers. Major remaining configuration gaps include Deployer infrastructure, secrets, processes, resources, automation, and recipes; Monitor resource creation and credential issuance; and the boundary between Analytics administration and detailed reporting. These are distinct from operational investigation pages, which can remain product-owned when Core provides a bounded summary or authorized link.

This is a source inventory only. It does not establish deployment, migration, customer-data, route/action, authorization, or automated-test acceptance.

## Scope and evidence

Reviewed `app/Core/Services/WorkspaceAdministrationCatalog.php`, Core workspace administration routes/controllers/contracts/views, `docs/unified-application-plan.md` (especially the requirement to replace remaining catalog handoffs with module-backed Core pages/actions and sections 4, 7, and 8), `docs/implementation-remaining-2026-09-25.md`, `docs/feature-parity-matrix.md` (D02–D25, M01–M21, A01–A11, C01–C03), and product route/controller/action/provider source under `app/Modules/{Deployer,Monitor,Analytics}`.

Status terms used below:

- **Core management** means Core has a workspace page and an action/provider that calls product-owned behavior for that scope.
- **Core summary / partial** means Core provides a bounded view or limited mutation, while the native page still owns additional administrative behavior.
- **Native handoff** means the catalog sends the user to the product page. Existing source actions remain the authority; this is not Core page coverage.
- **Operational / investigation** means the page principally searches, visualizes, or investigates current/historical operations. A handoff for this category is not automatically an administration gap, though the relevant authorized Core summary/link may still be required by the plan.

## Cross-cutting Core pages not fully represented by product catalog entries

Core already has concrete Signal routes for workspace overview/directory/team/invitations, projects and resource links, subscriptions/plans, costs and budget, customer status-page management, Monitor status pages, feedback, workspace activity, shared notification inbox/filter/export, credential inventory and gated create/rotate/revoke, project blueprints, and account security/data export/deletion review. Core contracts/providers keep native DB behavior in product modules. These are real Core surfaces, but coverage may be a **bounded subset**: for example activity is not a full native task center, project blueprints do not replace app configuration, credential inventory is not every provider/integration lifecycle, and status-page delegation is not broad observability administration.

## Highest-impact remaining source slices

1. **Complete Deployer project/environment configuration.** Bounded preview, ordinary environment settings, and deployment controls are now Core actions for exact mappings. Add process/resource definitions, remaining runtime/lifecycle controls, and appropriately scoped secret handling through product-owned actions. Keep plans/approval, provider effects, and queued operation state native; do not duplicate project mapping/blueprint behavior.
2. **Complete Monitor application, environment, credential and check administration.** Bounded existing-resource edits now run through typed Core provider operations and native authorization. Add creation/archive/restoration where appropriate, `CreateIngestToken`/`RotateIngestToken`/`RevokeIngestToken`, and check-token services. Preserve one-time secret display, Core/native workspace mapping, check plan caps, scoped external probes, and deletion/restoration fences.
3. **Deployer infrastructure lifecycle groups.** Treat domains/DNS/TLS; providers/servers; database operations; backups/recovery; and load balancers as separate high-risk slices. Reuse named actions (`SaveWebsiteDomainAction`, `SynchronizeWebsiteDomainAction`, `CreateProviderAction`, database operations, `Actions/Backup`, `Actions/LoadBalancer`) via typed module providers. These can make real external changes, so each slice needs an explicit preview/confirmation/retry contract, not simple CRUD mirroring.
4. **Deployer integrations, automation, and reusable recipes.** Separate configuration from read-only operational history. Native sources include `AutomationController` and `Actions/Automation`, repository/GitHub controllers, `RecipesController`/`RecipeGalleryController`, and `Actions/Recipe`. Integration credentials and recipe scripts require product-owned secret storage, explicit one-time return, and current source roles.
5. **Complete the capability/acceptance audit.** The feature matrix now records the bounded Deployer and Monitor configuration additions alongside prior Core Monitor and Analytics management. Reconcile every remaining Deployer handoff (D04–D19/D21–D23) and product route/provider against the matrix. Then exercise each real Core route against owner/admin/member/viewer roles, plan entitlement, exact workspace/resource mapping, product outage, stale state, destructive confirmation, and side effects. Do not count a catalog link, a typed read projection, or an authored test as page/action parity or acceptance. Core SLO and maintenance administration have source implementations; calculation, suppression, reporting, and browser acceptance remain separate.

### Bounded-list limitations in current Core Monitor administration

Core Monitor administration now uses bounded, server-side searchable pages for alert rules, environments, destinations, metric series, objectives, verified recipients, delivery history, and entitled audit history. The pages expose explicit page links and stable ordering; rules/destinations/audit/delivery records use 20–30 items per page and picker queries use 25. Alert forms retain currently authorized selected environment, metric series, objective, primary destination, and escalation values even when the selection falls outside the visible picker page or search result. Destination forms likewise retain recipients selected by destinations on the current page. Search and page values are validated and preserved in pagination links. This closes the previous fixed-cap reachability gap while leaving native workspace/resource authorization and plan checks as the source of truth.
