# Product module contracts progress — 25 September 2026

Core no longer imports concrete Monitor or Analytics delivery consumers. The new `ProjectConnectionDeliveryConsumer` contract declares supported event types, capability, target product, and a consume operation. Each product registers its own handler with the Core registry; Core resolves the destination from the active mapping and capability, checks the target product is enabled, then delegates. The product handler still performs the authoritative project/resource/plan checks and writes its receipt or annotation in the product database transaction.

A tokenizer-based architecture guard now scans Deployer, Monitor, and Analytics PHP sources for direct references to peer-module namespaces and explicit `DB::connection()` or `Schema::connection()` access to another product database. Composer exposes the check, and a dedicated GitHub Actions workflow runs it for pushes and pull requests. Registry regressions cover exact route selection, multiple incident event types, and duplicate handler conflicts. They are authored and intentionally unrun until the implementation plan is complete.

Core's source-event delivery and reconciliation commands now use product-owned outbox-source adapters for event discovery, claims, retries, lease recovery, and repair scans. The adapters normalize product records into a Core-owned immutable event DTO; dispatchers no longer accept product Eloquent models. Deployer and Monitor register their adapters with the Core registry from their module providers, and Core contains no concrete imports of those event models in these command paths.

PHP syntax, Pint, Composer metadata validation, Laravel application bootstrap, the module-boundary scanner, and `git diff --check` pass for the adapter slice. Dispatcher and reconciliation regressions were updated to use the normalized event contract and remain intentionally unrun. Product modules now register their outbox dispatch adapters through a Core contract; both delivery and repair commands resolve the adapter by registered product and no longer select concrete Deployer/Monitor dispatcher classes. Registry coverage is authored and remains unrun under the plan-wide deferral. The scanner does not prove isolation for dynamic connection names, unqualified queries, migrations, or runtime jobs; database-engine integration coverage remains a separate acceptance gate.
