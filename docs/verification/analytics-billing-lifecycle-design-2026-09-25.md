# Analytics workspace billing lifecycle — design and acceptance gates

This records the Analytics-specific billing source boundary. Deployer and Monitor keep their own workspace subscription records and provider workflows; Analytics must update only the `analytics` Core subscription slot. Existing imported Analytics workspaces retain their no-charge `legacy_access` snapshot unless a verified Analytics subscription is reconciled. No Analytics paid price or commercial terms have been supplied, so purchases remain disabled by default and no production charge is authorized by this source work.

## Current source checkpoint

The feature branch contains the configured-plan catalog, exact Core/native billing authorization, Stripe Checkout/portal/cancellation adapter, durable checkout attempts, signed webhook verification, Analytics-only Core subscription projection, bounded pending-event reconciliation, and a Signal billing page linked from Core Plans only for authorized product members. Commit `102f63f` adds provider-verified renewal of a terminal paid slot and operator inspection/recovery of aged Checkout attempts. Web routes require Core authentication and an enabled billing or webhook flag; the webhook route has its own flag. An empty catalog, disabled flags, and absent provider credentials keep purchases closed. A Monitor billing-controller dependency import was also corrected.

Astra's read-only passes found and prompted fixes for concurrent stale projection, uncertain checkout retries and expiry, deletion while a checkout is unresolved, checkout-time snapshot drift, retry starvation, first-observed canceled/unknown-price legacy fallback, an unknown-price transaction rollback, and replay after provider idempotency retention. Source acquires a SQLite-effective write reservation before checkout and webhook plan-slot reads; saves purchased terms on the attempt; keeps unresolved attempts exclusive; requires provider-confirmed expiry without a subscription; commits a denied paid slot for verified unapproved prices before asking for retry; and stops no-session create retries after 12 hours pending operator reconciliation. Terminal paid renewal now requires an exact Stripe account/customer/subscription/workspace binding and no other live Analytics subscription. The operator command may bind a verified matching Session; a negative provider inventory, including with `--apply`, leaves the attempt exclusive and exits unresolved. A recovered complete Session remains exclusive until the exact Core paid subscription is projected. Provider inventory is capped and fails closed; a provider outage makes the purchase control unavailable without making the billing page fail. Astra's re-review found no remaining P1/P2 in this source slice after the fixes and an unrun fixture repair.

Static PHP lint, Pint, module-boundary checking, route registration with flags both on and off, Blade compilation, and whitespace checks passed. Regression tests were authored but have not been run, and the additive Core migration has not been applied. No paid plan, provider credentials, checkout, or charge were enabled in production.

## Source design

- Keep `ANALYTICS_BILLING_ENABLED` false by default and independent of `ANALYTICS_PLAN_AUTHORITY`. The latter controls whether Analytics reads Core entitlement snapshots; it must not enable checkout. Missing provider credentials, account identity, allowlisted price, or valid immutable plan snapshot closes the purchase path.
- Map each configured Analytics price ID to a specific plan key, display terms, entitlements, and limits in a product-owned catalog. The browser selects a catalog plan key; it cannot submit a price ID, billing account, entitlement, or limit. Unknown prices never grant a plan.
- Resolve exactly one current native Analytics workspace and actor to one active Core workspace and user. Require current native membership plus the Core workspace billing role for checkout, portal, and cancellation. A matching email, stale identity map, or product grant alone cannot authorize billing.
- Bind provider account, customer, and subscription IDs to that exact workspace and product. Freeze the chosen catalog snapshot on the checkout attempt so later configuration edits cannot change the plan purchased. Keep checkout attempts idempotent and return targets authenticated and host-allowlisted. A timeout or uncertain provider response must retain the attempt and block a second payable session until provider state is known. An unresolved payable attempt also blocks workspace deletion. A browser success callback clears or displays checkout state but never grants entitlements.
- Verify webhook signatures and provider account identity before recording events. Deduplicate by provider event ID, serialize provider fetch plus Core projection per workspace across workers using a lock that also works with the deployed SQLite Core database, reject customer/workspace/account conflicts, and handle replay or out-of-order events without regressing the current plan. [Stripe documents](https://docs.stripe.com/webhooks#event-ordering) that separate events can share the same creation second, so event timestamps alone cannot establish order or deduplication. Persist event receipt and the Analytics-only Core subscription/snapshot assignment atomically. A provider outage or unresolved binding leaves the current verified entitlement unchanged and records a retry/review state; bounded retries must not starve older pending receipts.
- Preserve legacy access on the unaffected workspace during rollout, while ensuring a canceled or expired paid subscription cannot silently regain the unlimited legacy snapshot, including when the first verified paid subscription event arrives after cancellation. Product-owned event processing must remain recoverable after a worker crash and must respect active/deleting/deleted Core workspace fences.
- The deployed Core database is SQLite. A transaction that reads first cannot rely on `SELECT FOR UPDATE`; checkout reservation and webhook projection must acquire a real write reservation before they read the plan slot or fetch authoritative provider state. Bound provider timeouts and retry busy failures safely. During enablement rehearsal, measure the effect of a slow provider response on other Core writes before turning on checkout.
- A canceled or incomplete-expired paid slot can enter a new checkout only after the current Stripe subscription is verified terminal, its account/customer/attempt/price/workspace binding matches, and the customer has no other live Analytics subscription. A scheduled cancellation or any live/provider-uncertain state remains blocked. Rehearse the renewal and webhook projection before enabling paid plans for customers.
- An attempt with no locally recorded Checkout Session may be provider-uncertain after a timeout. Replaying its create request is time-bounded because provider idempotency retention is finite; an older unresolved attempt stays exclusive. The operator command inspects the configured Stripe account, scans a bounded inventory, and may attach a verified matching Session. An empty inventory never proves that an indeterminate create failed and never releases the slot. Define a provider-specific manual resolution path and runbook for no-match attempts before enabling purchases; age, a short waiting period, and stopped local workers alone are not sufficient.

## Deferred acceptance

Author regressions for exact role and identity mapping; forged price/return/account values; fixed-quantity licensed price and supported currency validation; checkout retry, uncertainty, concurrent requests, and session expiry; success-without-webhook; signature failure; duplicate, stale, conflicting, concurrent, and reordered events on SQLite as well as the target production engine; provider retrieval failure; canceled/expired status; first-seen canceled subscriptions; cross-product subscription isolation; deleted workspace and pending-checkout deletion fences; missing configuration; and legacy access retention. Do not run the automated suites until the unified plan's source implementation is complete, as requested. Before enabling purchases, run the suites and migration rehearsal on four isolated databases, compare provider customer/subscription state with Core, verify the approved price IDs and published terms, perform a real checkout/portal/cancel and webhook replay drill, and confirm that Deployer and Monitor plans do not change.
