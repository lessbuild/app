# I13 developer API — static route and delivery inventory

This is a source-level inventory, not API compatibility acceptance. It compares registered product endpoints with the documentation source on the feature branch at `92b648f`. The comparison did not issue API requests or run automated tests or migrations.

| Product | Current developer-facing contract | Static finding | Deliberate boundary |
| --- | --- | --- | --- |
| Deployer | `app/Modules/Deployer/Routes/api.php` and `public/openapi.json` | All 19 authenticated `/api/v1` method/path pairs in the route source have a corresponding OpenAPI operation, with no extra documented v1 method/path pair. Core Help renders this product-owned contract and its configuration example. | `/api/health`, GitHub App callbacks, and repository webhooks sit outside the authenticated v1 control-plane contract. Core Help describes the inbound webhook setup separately. Method/path agreement does not prove scopes, payloads, errors, or client behavior. |
| Monitor | `app/Modules/Monitor/Routes/api.php` and `OpenApiDocument::make()` | Seven ingestion, receipt, deployment, heartbeat, and queue method/path pairs appear in both the route source and generated document. Core Help includes an ingestion example and the outbound signed-alert protocol. | Health, the generated schema endpoint, and Stripe billing callback are outside the seven machine-ingest operations. Generated schema coverage still needs runtime request/response comparison. |
| Analytics | `app/Modules/Analytics/Routes/api.php`, `AnalyticsApiDocumentationProvider`, and `public/tracker/v1.js` | The documented POST/OPTIONS collection pair matches the API route source; the documented browser tracker is a static public asset. Core Help includes a server-side collection example. | The public site ID is not a bearer credential. The OpenAPI endpoint and flag-gated Stripe billing callback are infrastructure endpoints rather than collection operations. |

Core's credential mutation inventory currently supports a Deployer personal access token and Monitor ingestion token creation plus the supported Monitor queue/heartbeat key rotation or revocation paths. It does not prove that every legacy credential family has a Core mutation path. Analytics collection uses a public site ID and origin checks, so adding a generic bearer token to that endpoint would change its contract.

The 19 Deployer OpenAPI operations declare the same `read`, `deploy`, or `manage` ability required by their controller, form request, or configuration-route middleware in the current source inventory. `ControlPlaneAccess` also checks current workspace claims, an optional project allowlist, API entitlement, and workspace network policy. This is a source comparison, not a live authorization or revocation test. Deployer's API middleware applies the plan-based `api` rate limiter; response headers and limits under each workspace plan still need runtime acceptance.

Deployer's collection contract has a concrete pagination gap: `GET /projects` loads every visible project with `get()`, while `GET /deployments` returns the newest 100 builds with no way to request the next page. Neither OpenAPI operation defines page or cursor inputs or continuation metadata. Add an explicit versioned pagination contract and compatibility path for existing v1 clients; silently changing their response shape would break callers. The published Deployer schema also leaves most response bodies described only in prose, so a route/scope match is not response-schema parity.

The Core delivery-history page shows Deployer **inbound repository events** and Monitor **outbound signed alert deliveries**, with source-app links and Monitor's authorized retry. Deployer's separate outbound `DeliverAlertWebhookJob` sends a signed payload but stores only latest destination success/failure fields; it has no durable per-delivery row or controlled replay. An outbox and attempt ledger must be owned by Deployer before that flow can be projected into Core history. Incoming Git-provider events must not be presented as replayable outbound notifications. See [delivery-history progress](workspace-delivery-history-progress-2026-09-25.md).

The next contract audit must compare runtime auth and scope enforcement, request and response examples, error envelopes, pagination, rate-limit headers, expiry and revocation, and idempotent retries for every operation against the published schemas. It also needs representative public clients and cross-product integration examples. A matching route list, source-level scope comparison, or authored regression is insufficient evidence for those behaviors. Automated suites remain deferred until the full source plan is complete.
