# Deployer blueprint recipe reuse — design and release gates

Core project blueprints can name Deployer recipe IDs for selected canonical environments. The earlier provider only returned manual review/install instructions; this source slice prepares the references as native snapshots. Deployer recipes are attached to servers through native workflows, while a blueprint can create an environment before any server is selected. A blueprint must therefore prepare a reviewed recipe for a specific accepted environment without claiming that it ran on infrastructure.

Source commit `cc20349` contains the snapshot, manual copy, privacy, export, deletion-preflight, and replay-recovery slice. PHP syntax, formatting, diff, and module-boundary checks passed; its regression tests were authored but not run. It is not deployed, and the release gates below remain open.

## Source boundary

- Keep the script and prepared snapshot encrypted in the Deployer database. Core may retain only a bounded keyed fingerprint and generic result message; it must not receive script text, ciphertext, or secrets.
- Preview checks the current actor, organization, recipe ownership/publication and revision, and selected environment. A new environment may have no canonical ID at preview. Apply checks the accepted canonical target and current native identity, then fails on source drift before the first write. Core records new resource mappings after Deployer commits its receipt. Receipt replay must accept only the authentic fully-unrecorded recovery state or an exact active mapping; partial, conflicting, or archived mappings fail closed.
- Apply writes an immutable, ordered Deployer-owned binding keyed by blueprint step, native environment, and source recipe. A completed step replays its saved binding without refreshing it from later source edits or resurrecting a deleted source. Source IDs remain historical provenance; deleting a recipe must not cascade away an applied snapshot.
- Under shared Core authentication, the native project/environment page shows only bindings that the current actor may view and that still match active canonical mappings, through shared Signal components. It never displays decrypted script by default. A separate POST can copy one saved snapshot into an unpublished workspace recipe after current Core/native authority, native deploy permission, deletion fences, and any protected-environment approval check. A personal-source snapshot requires explicit acknowledgement before it becomes visible to workspace members. Repeating the action returns the existing copy; it does not attach to a server or execute a script. Legacy-mode project pages retain their old data dependencies.
- Workspace export includes safe binding/copy metadata only; an unshared personal snapshot stays out of that export, and a personal sharing receipt must validate before its metadata is included. The native page and export skip the new table before its additive migration; a recipe-configured apply fails closed until the table exists. Environment deletion removes its bindings. Account/workspace deletion must reconcile references before purging an actor or workspace, and must not silently delete another team's prepared work.

## Open release gates

The initial account-deletion fence can leave a blueprint preparer or the original recipe author blocked when their snapshot remains in another workspace, including a production environment that cannot be removed on its own. Historical `actor_source_id` and `source_user_id` both need a resolution policy even if the source recipe has since been deleted. Before deployment, add a manager-authorized, audited per-binding archive path that resolves this without deleting a production project. Require exact current mapping, deletion-fence checks, and destructive confirmation. A manager must be able to archive a personal binding without seeing its script or private metadata.

Archive should atomically delete the active snapshot and its encrypted script and identifying provenance, then retain a separate signed tombstone with an opaque commitment to the accepted blueprint slot. This avoids changing the active row's binding fingerprint contract or keeping identity and recipe details in a terminal row. Serialize apply/replay, install, archive, and custody changes on the same stable native parent; replay must find exactly one authentic active snapshot or tombstone per slot and must never recreate or install archived content. Tombstone references can still be linked through retained step and environment records, so their retention must be handled explicitly. Author focused regressions for privacy, malformed or transplanted evidence, concurrent install/archive, recovery before Core mapping, and account-deletion preflight.

Archiving a binding alone does not unblock account deletion when a copy was already installed: `recipes.user_id` is a non-null foreign key to the preparer, and Deployer also blocks foreign-workspace recipe ownership. An installed unpublished workspace copy needs a separately confirmed, audited custodial transfer to the acting, currently authorized real workspace manager or a safe native transfer/delete path. Preserve the copy's edits and attachments, and do not recreate a missing copy. Original private organization recipe ownership also needs an explicit transfer/delete path. Published or formerly published gallery authorship remains a separate blocker until an explicit retention/delete policy exists. Do not silently reassign authorship or describe snapshot archive as sufficient account-deletion recovery.

Deployer's encrypted scripts, snapshot cast, custom HMACs, and accepted Core authority evidence depend on the application key. Introduce versioned signing-key verification and a controlled re-encryption/re-signing process before rotation; a decryption fallback alone will not preserve existing HMACs or pending accepted attempts. Do not rotate the key during this source work. Author regressions for new-environment preview/apply, source drift, saved replay, duplicate prevention, personal/org visibility, manual install, deletion/export, and invalid encrypted data. As requested, keep automated suites and migrations deferred until the full unified source plan is complete. Migration, production data, native browser, and server-operation acceptance remain separate release gates.
