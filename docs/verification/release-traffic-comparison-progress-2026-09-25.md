# Release traffic comparison progress — 25 September 2026

Monitor deployment detail compares Monitor's own release-tagged request and exception telemetry and connected Analytics outcomes around a recorded deployment. Monitor's summary uses the same environment and service identity on each side of the deployment; it reports request records, HTTP 5xx/error-or-critical flags, average duration among nonnegative timed request records, exception records, distinct issue IDs, and request/timed sample counts. The UI notes that request spans may include internal or outbound records and are not unique user requests or availability checks.

Core resolves only active project mappings and connections. It rechecks the viewer's project membership and Monitor/Analytics product grants, then requires the Analytics `traffic_context` entitlement and the Monitor `deployment_context_minutes` limit. The requested before/after interval is capped by both that plan limit and the elapsed time since the deployment. A disconnected site, revoked grant, missing plan capability, unavailable Analytics database, or absent authorized mapping yields the generic empty state.

Analytics returns aggregate counts only: pageviews, distinct non-null visitor hashes, goal conversion events, and distinct converted visits. Event eligibility now follows Analytics' own Overview report: events without an ingestion-batch link and events from processed batches are included, while pending and failed batches are excluded. The provider also reports accepted, processed, pending/processing, and failed batch counts using `accepted_at`, keeping intake-time evidence distinct from the event-time metrics. The deployment page explicitly distinguishes no accepted batches from confirmed zero site activity and states that accepted batches cannot establish tracker delivery, sampling, or full event-time coverage. Its latest successful-batch timestamp is labeled as a site-wide activity time, not a processed-through watermark. When a connection is eligible, Monitor and Analytics use the same UTC before/after boundaries; the Monitor telemetry window is narrowed to respect the connected plans. The page links to the access-checked Analytics site dashboard and lists same-environment incidents overlapping the comparison and other deployments of the same service in those windows. Delays, sampling, visitor mix, and overlapping releases can affect observed differences; the page does not claim causality or expose visitor-level data.

Regression cases were added for Monitor's equal half-open windows and same-service/environment filtering, latency/error formulas, plan-bounded Analytics windows, explicit connected-site lookup, processed conversion filtering, converted-visit counting, Analytics Overview report reconciliation (including legacy events without batch links), no/partial/fully processed intake messaging, the Analytics dashboard workspace resolver rejecting a deep link after the Core product grant is revoked, and Analytics query/lost-connection failures degrading to an empty optional deployment context. They are authored and intentionally unrun while the plan remains incomplete.

This advances I5 but does not complete its acceptance gate. Intake accounting now distinguishes no accepted batches, incomplete batch processing, and batches whose current status is processed, while explicitly leaving tracker delivery and event-time coverage unknown. The source-report reconciliation, revoked-grant destination, and provider-outage regressions are authored but remain unverified until tests may run. Still open: complete role, revoked-connection, product-outage, and production-engine acceptance; and stronger completeness signals if Analytics later records a trustworthy tracker heartbeat or capture watermark. The deployment view labels UTC explicitly; workspace-local timezone selection is not implemented.
