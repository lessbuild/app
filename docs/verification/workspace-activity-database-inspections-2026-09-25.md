# Deployer database operation activity progress

Deployer now records durable operation runs for database inspections and credential setup/removal in its own database. Requests create queued records before dispatch; workers record attempts, running leases, and terminal success/failure. Queue-dispatch failures are retained as failed runs. Successful credential removal remains in the operation history after the credential itself is deleted. Operation records contain resource and opaque subject IDs but no database username, password, SQL, schema names, metrics, or remote error text.

Core projects queued, running, succeeded, failed, and stale/lease-expired operation runs only through currently accessible, explicitly mapped MySQL/PostgreSQL environments. Terminal history is bounded to 30 days. Stale queued or expired running records appear as unknown progress instead of implying that work is active. The result link returns to Deployer's database operations page, where product authorization and retry controls remain authoritative.

`buildpusher:databases:reconcile-operations` runs every five minutes and re-dispatches a bounded set of queued runs older than two minutes or running runs with an expired lease. Unique queue locks and a transactional row claim suppress duplicate execution; database-user jobs also serialize remote changes by credential. A worker exception returns the run to queued for Laravel's retry path, while exhausted jobs store a generic failed state. The Deployer database page now exposes an owner-authorized, entitlement-checked retry for unapplied credentials using the existing encrypted password, and duplicate submissions reuse the active operation. Inspection and removal can be retried through their existing product actions. No migration or production scheduler change has been applied as part of this code work.

Authored regressions cover mapped inspection and credential runs, old-history exclusion, unmapped environments, unsupported resource types, active and failed states, stale progress, result links, redaction, successful worker transitions, stale-run reconciliation, credential retry authorization, and repeated-submit coalescing. All remain unrun until the full plan is complete. Retry controls for other task types and cross-database tenant/reload acceptance remain open in I8.
