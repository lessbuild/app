# Core support and administration surfaces progress — 25 September 2026

## Implemented in the working tree

- Core serves `/help`, `/help/deployer`, `/help/deployer/api`, and `/help/monitor/api`. The Deployer guide/API reference and generated Monitor API reference render with the Buildpusher Signal public navigation; Deployer's old `/docs` and `/api-docs` paths and Monitor's settings API page hand off to Core. Deployer and Monitor OpenAPI JSON endpoints remain product-owned and keep their established routes.
- Core serves the platform `/status` page and JSON report by aggregating one status provider per enabled product, plus `/status/{product}/{slug}` for published Monitor and Deployer customer pages through typed providers. Deployer keeps its existing component diagnostics. Monitor and Analytics readiness probes use their public product endpoints with one-second connect and three-second total-request timeouts; an unavailable product becomes one generic degraded component while other apps still report. Snapshots cache for 30 seconds. Monitor `/api/health` and Analytics `/ready` expose only coarse database, cache, and background-processing check states; internal queue names and exception details stay private. A product-owned heartbeat row is refreshed by a queued probe for Monitor’s three worker lanes and Analytics’ worker lane, scheduled once per minute, so a database-only success no longer masks a stopped queue worker. Existing Monitor public URLs redirect to Core. Existing Deployer public URLs keep rendering at `/status/{slug}` with the Core Signal view, retain their subscription and JSON report flows, and use the Core provider over Deployer-owned tables. Both products retain their status records and admin workflows in their own databases.
- Core workspace management now includes a Deployer customer-status workspace screen. Authorized, exactly mapped Deployer owners/admins can create, edit, publish, and delete pages, select only websites in the mapped organization, and create or update incident and maintenance timelines. These operations delegate to the existing entitlement-checked Deployer actions, so confirmed-subscriber notification, resolution timestamps, and product-owned rows retain their current behavior. Core members without local Deployer manager authority can read the status history but cannot mutate it; ambiguous identity or workspace mappings fail closed.
- Core serves `/workspaces/{workspace}/manage`, grouping shared project/team/plan/cost/feedback controls with product administration links. The catalog covers Deployer organization and release controls, infrastructure and recovery, costs, automation, activity, notifications, and account/billing surfaces; Monitor applications, telemetry, incidents, status pages, alerting, objectives, integrations, data, team, and billing; and Analytics sites/reports, setup, goals, data controls, exports, team, and account settings. Analytics entries with site-specific controls intentionally open its site-selection dashboard because those routes require a selected site identifier.
- Core now also manages Monitor customer status pages for mapped workspace owners and admins. Core reads only safe monitor labels, types, environment context, and high-level health; create, update, and delete delegate to Monitor's existing `ChangeStatusPage` service and workspace policy. Selected public monitors are constrained to the mapped Monitor workspace, and status records remain in Monitor's database.
- Administration links appear only when the current Core membership has an active grant for that product, use exact configured product origins and shared-auth handoff, and rely on each module's existing authorization after handoff. The links are an index into current module screens, not a replacement of product-owned mutation flows.
- Core serves `/workspaces/{workspace}/costs`. Deployer registers a typed `WorkspaceCostBreakdownProvider` which requires exactly one reconciled organization mapping, exactly one Deployer user mapping, local organization membership, and active Core Deployer access. The provider reads catalog estimates and preview usage from Deployer's database and writes budget changes through the existing Deployer action and entitlement check. No Monitor or Analytics monetary report is invented where no provider exists.
- Core serves `/workspaces/{workspace}/feedback` with encrypted descriptions, reproduction steps, and review responses in a new Core table. Members can submit only for an app to which they have active workspace access. Non-managers see only their own submissions; workspace owners/admins can review and delete workspace submissions. The Deployer feedback schema, routes, and records remain intact as a compatibility source until a verified history importer is implemented.
- Core now also displays a bounded, read-only view of historical Deployer feedback when exactly one reconciled organization and user mapping exists and the current Deployer workspace access is valid. Non-reviewers see only their own legacy records; managers can open the original Deployer review page with its mapped organization selected. The provider reads Deployer's encrypted casts, leaves source rows unchanged, and fails closed on unavailable databases or decryption errors.
- A single native disclosure component renders the current workspace and menu in both the desktop topbar and mobile navigation drawer. It shows the active workspace, available workspace count, selected-state mark, and a manage-workspace link.

## Product worker liveness added — 25 September 2026

Monitor now schedules one liveness job for each of its telemetry, checks, and alerts workers; Analytics schedules one for its analytics worker. Jobs update a product-local heartbeat table, unique jobs prevent routine probe buildup, and readiness turns background processing degraded when a heartbeat is missing or older than the configured threshold. Core maps only allowlisted check keys to Signal status components and reports generic descriptions. Health responses are uncached and omit queue names, credentials, and exception messages.

Regression tests were authored for fresh/stale/missing heartbeats and Core check-name allowlisting; they remain unrun until the unified plan is complete. Pint and PHP syntax checks passed for all PHP files changed in this progress slice. Route inspection confirms Monitor `/api/health` and Analytics `/ready` are mounted on their configured hosts; `schedule:list` confirms both per-minute health probes are registered. `git diff --check` passed. No test command was run. The migrations and scheduler probes have not been deployed.
