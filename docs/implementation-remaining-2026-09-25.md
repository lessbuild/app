# Remaining source implementation

This checklist separates missing source behavior from pending validation in the unified application plan. It does not narrow the approved plan or authorize skipping product features. Automated tests remain deferred until source implementation is complete; test execution, browser acceptance, migration rehearsal, and production configuration remain subsequent acceptance work.

## Remaining approved shared capabilities

1. **Core administration.** Replace the remaining administration catalog handoffs with real Core pages/actions backed by module-owned operations. Core now manages Monitor alert rules, destinations, maintenance windows, service-objective desired state, settings, audit/exports, bounded edits to existing mapped applications/environments/checks, Analytics sites/goals/export orchestration/site deletion, and bounded Deployer project preview/environment/deployment-control settings for existing mapped resources. The catalog still hands off broad Deployer organization, infrastructure, automation, recipe, secret, process, resource, and runtime configuration; Monitor resource creation and credential issuance; and operational investigations that need an explicit Core summary or authorized native link. The [catalog coverage audit](verification/core-administration-coverage-audit-2026-09-25.md) distinguishes management pages from summaries and native handoffs. Do not infer Core action parity from a catalog link. Monitor maintenance and SLO administration have authored, unrun regressions; SLO reports, burn-rate investigations, and exports remain Monitor-owned.
2. **Versioned project blueprints (I11).** Core stores versioned definitions, previews exact canonical environment bindings and product plan impact, and processes durable, idempotent Deployer/Monitor/Analytics steps with retry receipts. Deployer applies safe application templates and environment/process setup; Monitor can create optional HTTP checks; Analytics can create sites without marking domains verified. A new Deployer source slice prepares encrypted, environment-bound recipe snapshots and exposes an authorized manual copy into its workspace library; blueprint application neither attaches recipes to servers nor runs scripts. The terminal per-binding archive, installed-copy custody/author transfer, and account-deletion recovery path remain a release gate, as do partial-failure recovery, limits, mapping conflicts, secrets, subscription isolation, and real domain/tracker verification against migrations and customer data. See [recipe reuse design](verification/blueprint-recipe-reuse-design-2026-09-25.md).
3. **Consistent developer API experience (I13).** Core now offers scoped create/rotate/revoke for supported Deployer and Monitor credential families, with product-owned issuance/receipts, current access checks, and one-time secret display. Core's delivery page already summarizes Deployer's inbound repository events and Monitor's signed outbound alert deliveries; Monitor has a native authorized retry. Deployer's outbound alert-webhook job still has no durable per-delivery ledger or authorized retry path; its DNS check is not pinned to the HTTP connection and its response is unbounded. It needs a product-owned outbox/attempt contract and hardened transport before Core can show that history. The broader approved I13 scope also needs a contract-by-contract audit of existing APIs and credential families, integration examples, and compatibility evidence for auth, errors, pagination, throttling, expiry, and idempotency. A source comparison found Deployer's 19 documented v1 scopes aligned but its project list unbounded and deployment list capped at the newest 100 without continuation; add a versioned pagination contract without silently breaking existing clients. Analytics has no equivalent machine-credential mutation provider in this source slice; avoid presenting the Core page as universal token management. See the [static route and delivery inventory](verification/i13-developer-api-route-audit-2026-09-26.md).
4. **Independent billing lifecycle.** The separate workspace plan slots and entitlement adapters exist, and Deployer Core-mode billing is implemented behind its authority switch. Analytics now has a disabled-by-default source slice for a configured paid catalog, exact Core/native billing access, licensed fixed-price checkout, portal and cancellation, signed Stripe event reconciliation, immutable checkout terms, and Analytics-only Core plan projection. No paid prices or credentials are configured. A canceled paid Analytics slot cannot yet start a new verified subscription, and aged provider-uncertain checkout attempts need an operator reconciliation path. Complete those lifecycle operations, approve published terms and provider IDs, then rehearse the four-database migration and provider state before enabling purchases. Monitor and Deployer still require end-to-end ownership, reconciliation, and subscription-isolation acceptance.

## Items that are not missing source features

- The new Core blueprint routes/services and three product providers, credential mutation routes and two product providers, and Core Monitor/Analytics administration pages are source implementations, not merely catalog links or proposals. Their authored regressions have not been run under the requested deferral, and production migrations, role/entitlement matrices, browser flows, and full feature-parity acceptance remain pending.
- Analytics site deletion now has an immutable native operation, export-file manifest and verified cleanup, retry scheduling, and Core accept/status/retry actions. Export pruning protects ownership rows until files are absent. Deployer has a bounded Core deployment-controls page for exactly mapped active environments that delegates to its native action. Its new project/environment configuration directory covers mapped preview and ordinary environment settings; Core environment selection is active-only, native type changes are read-only in Core, and existing canonical/native type mismatches are hidden until reconciled. Secrets, processes, resource placement, and the rest of Deployer configuration remain native or open Core work. Monitor now has a Core directory and edits for existing exactly mapped applications, environments, and checks; it preserves native authorization and check mutation rules but does not create or archive those resources or issue ingestion/check credentials. These source slices still require the deferred behavioral and production-engine checks.
- Coordinated account/workspace deletion now has a source implementation with immutable Core requests, two-phase module preparation/purge, source fences and receipts, identity-projection and native activity barriers, receipt-based recovery after logout, billing reconciliation, and retained tombstones. Deployer's product-local deletion hands off to Core. Source review is complete; additive migrations, concurrent worker/fault-injection tests, and browser/customer-data acceptance are deferred. See [deletion design and recovery limits](coordinated-deletion-design-2026-09-25.md).

- I3 native notification projection now merges Deployer recipient notifications into Core without replacing native read state or delivery channels. I12 now adds authorized Deployer infrastructure and recent deployment relationships, bounded and filtered by current access, alongside the existing Monitor/Analytics resource mappings. Both have reusable Signal presentation and authored, unrun regression coverage; see [inbox and infrastructure progress](verification/native-inbox-infrastructure-progress-2026-09-25.md).

- Monitor application/environment restoration is now implemented through durable Core requests and native receipts, retained archive views, current manager authorization, explicit shared-project restoration, and fenced recovery. Native child archive/pause states and revoked credentials/checks are preserved. The additive migrations and deferred acceptance remain pending; see [restoration progress](verification/monitor-restoration-progress-2026-09-25.md). Analytics has no native restore action; collection pause/resume remains supported. Deployer backup restoration and release rollback remain ordinary authorized operations.

- Archived-data exports, recipient-scoped Monitor digests, Deployer history/shared-resource controls, direct dependency checks, and nested source projections are implemented. Independent review identified and closed concrete dependency and local-metadata permission regressions. Current membership/product grants remain mandatory; the export exception does not authorize interactive mutation. Deferred behavioral and performance acceptance remains distinct from source implementation.
- Workspace feature rollouts (§7.2) are implemented for shared credential inventory and delivery history: workspace preferences, server availability/pilot/management policy, audited changes, and daily exposure/outcome metrics. Existing views remain enabled by default; flags neither grant entitlements nor change background delivery. Migration and deferred validation are still required before release.
- I5 release comparisons are implemented in Monitor deployment details, including equal windows, source metrics, connected Analytics traffic/conversions, overlap context, and coverage limits.
- I14 transfer execution is outside the approved initial behavior; versioned manifest export and destination dry run are implemented.
- Held identity and Deployer billing ownership, unpublished Analytics paid prices, and provider credentials are reconciliation/product/configuration inputs. They must be resolved before affected production behavior is enabled; the disabled Analytics billing source still needs renewal, uncertain-attempt reconciliation, and independent billing acceptance.
- Authored but unrun tests are deferred validation. The D19/C01 matrix rows now distinguish implemented Deployer investigation views and incident export, saved operational filters, per-product activation rollups, and registered module activity providers from broader acceptance and source work that remains open.

Once the source gaps above are closed, perform the full requirement-by-requirement audit in the main plan, then run the deferred regression/static/build/browser checks and production acceptance. Do not infer completion from a clean static check or a successful public-page request.
